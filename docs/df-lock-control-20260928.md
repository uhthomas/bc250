# Offline BC250 Data Fabric lock control

## Live result and current state (2026-09-28)

Later RAM-only PSP IPL-aperture diagnostics read `0x1f81c=3` at the **first
Trusted OS instruction**, before this UEFI driver can execute; a guarded
write-zero/readback at that point remained `3`. Thus the operational VCN
disable state predates the UEFI `LockDFReg` callback. See
[the VCN investigation](video-decode-next-step.md).

A second fault-free candidate boot (`3489ac2a-0b0d-4caa-a726-a4eb27071404`)
tested the omitted lock's possible effect on root-SMN writability. The Pico
completed 41,454/41,454 reads, and a guarded, volatile write of bit 11 to
`0x50d6c` read back the original `0xf0`, not the requested `0x8f0`.
The script restored and verified `0xf0` before exiting. Therefore this UEFI
call omission did not open a post-boot root-PCI write path to that word;
it still does not identify the VCN harvest source or establish whether this
specific UEFI callback ran. That candidate boot was healthy and the BIOS
EEPROM remains unchanged. See [the guarded probe](../tools/vcn-psp-diagnostics/probe_df_gate_after_lock_omission.py).

The corrected [early-release selector](../tools/pico2-interposer/burst_match_early_od.pio) supplied **both 20,727-read UEFI passes** from Pico QSPI on an exact-original control boot. Fedora reached SSH. This corrects the earlier inference that the long-stream handoff itself prevented boot: that inference came from the older late-release selector, which stalled after one pass even with original bytes. The early selector releases the original flash's CS# after matching 26 command bits, before the six low alignment bits; the final revision sets the first reply bit during the last command high phase. Its on-board control showed 41,454/41,454 completed reads with `fault=0`. The input-only sampler verified one 64-byte Pico reply on the wire; this is a sampled integrity check, not a capture of all 2.65 MiB of traffic.

The same selector then served the **equal-length DF-lock omission candidate**, with a 1,327,104-byte payload independently read back from reserved Pico QSPI (SHA256 `94693ac43e90236b77e6fc2be64c4ab8e48e18fd88b0ec6c3b95ae9af1e53ef9`). Its cleanest trial completed 41,454/41,454 reads, `fault=0`, maximum rearm 162 Pico cycles, and a second-pass 64-byte wire sample matched all 32 expected 16-bit words. Fedora booted (`d8bd138b-2c0b-4228-b756-bcdb8e74cd27`). **VCN still did not appear** among the eight AMDGPU IP blocks; `vainfo --display drm --device /dev/dri/renderD128` failed initialization. Post-boot root-SMN reads were unchanged: `0x50d6c=0xf0`, `0x511b4=0xffffffff`, `0x5a870=0xff`. This candidate has not enabled hardware decoding and is not a high-confidence BIOS flash image. The BC250 BIOS EEPROM was never written.

The Pi 5 was restarted to recover a vanished Pico USB device. The known CS# pass-through RAM image was then loaded and armed with Pico MISO input-only before a PDU cold cycle. Original-BIOS Fedora is healthy on boot `f695bd15-ce10-4b19-98b8-4fd3b37ca543` (`systemctl` running). The reserved Pico QSPI range still holds the candidate, but it is dormant while the passive RAM image runs.

The known-working 16 MiB ROM (SHA256 `f1251268fc129d6799fcb75041017ee739250d71b7c9d1981d67016923834183`) contains `AmdPspDxeV2` inside a GUID-defined LZMA firmware-volume section at SPI offset `0xae0078`. The extracted PE (SHA256 `554e1b4bc50d38578b09d58cc2fcdb0f460ad3c164eab9009be706a551dc1c92`) is byte-identical to the version extracted from the currently working ROM, despite the original extraction having a different full-ROM hash.

The module registers a PCI-enumeration-complete callback. The callback calls the function at PE offset `0x2244`, which prepares a `0x10`-byte PSP mailbox buffer and passes command `0x1b` to the mailbox helper at the call at PE offset `0x229f`. The adjacent firmware strings are `PspMboxBiosLockDFReg_START`, `Psp.C2PMbox.LockDFReg`, and `PspMboxBiosLockDFReg_END`. These facts identify a concrete UEFI request to lock Data Fabric registers. They do not prove that this callback actually ran on a particular boot or that the read-only `0x50d6c` value is governed by this lock.

An offline control replaces only the five-byte mailbox `call` with `mov eax,1`, preserving the success branch in the local routine. [The pinned generator](../tools/vcn-psp-diagnostics/prepare_df_lock_control.py) and [Unicorn check](../tools/vcn-psp-diagnostics/test_df_lock_control.py) verify the original and changed paths. [The ROM rebuilder](../tools/vcn-psp-diagnostics/build_df_lock_control_rom.py) recompresses the nested firmware volume and updates the containing section and FFS lengths and header checksum. The output is ignored under `output/video-decode-20260922/df-lock-control-20260928/`; the candidate SHA256 is `f3bf69891739c5143748bc975dc7030e1144fdfebf27c325dccad5d748aa7c64`.

The independent `uefi_firmware 1.16` parser accepts the rebuilt ROM and extracts the intended driver. Compared with the working ROM, the *decompressed* inner firmware volume changes at exactly five bytes (`0xaa077` through `0xaa07b`); the re-extracted driver changes only at PE offsets `0x229f` through `0x22a3`. The compressed outer file grows from 1,383,332 to 1,384,160 bytes and fits within the original firmware volume's erased free area. The PE has no certificate table and its checksum field is zero. These checks prove construction and parsing, **not** firmware boot behavior or a VCN fix.

A directly relevant [research experiment on Zen 5 EPYC](https://benschlueter.com/assets/paper/fabricked.pdf) also omitted `LockDFReg`. Their machine restarted before GRUB when that command alone was omitted and reached the OS only after they also omitted a later `BOOT_DONE`/ExitBootServices mailbox command. This is evidence of a possible boot dependency, **not** proof the BC250 behaves the same way. The BC250 module also contains an `ExitBootServices` mailbox path. The paper does not identify `0x50d6c` or establish that this BC250 register is a mutable DF configuration register.

That BC250 call-site is now pinned as well: at PE offset `0x8c1`, the module passes `edx=0x06` and its prepared buffer to the same `0x1f28` mailbox helper, adjacent to the `Psp.C2PMbox.ExitBootServices` string. [The separate two-command control](../tools/vcn-psp-diagnostics/prepare_df_lock_bootdone_control.py) replaces this call and the DF-lock call with local success values. Both call boundaries pass native x86 emulation, and the independently re-extracted 4,452,352-byte inner firmware volume differs at only those two call sites (eight byte values differ across the two five-byte instructions). The unflashed combined ROM SHA256 is `a586109cd0375fa9c4b30fb1c5e079201ed7f0e2d0e2d8c75ef77e9ebeaf5795`. It is also only an offline control; the EPYC boot result does not establish safe or useful BC250 behavior.

**Do not flash the candidate ROM.** The reversible interposer trial now boots, but it leaves VCN unavailable. The BC250 BIOS EEPROM remains unchanged by these trials.

## Read-only burst measurement

The [RAM-only Pico capture](../tools/pico2-interposer/cs_pass_burst_snapshot.c) was loaded and armed on the existing six-wire connection while the BC250 was idle. It passed the original flash's CS# through GP7 and left MISO input-only. One PDU cold cycle captured the `READ03 0xae0180` transaction; the sampler started two 64-byte bursts after its nominal target because the command observer reports the preceding transaction only at its end. The capture contains exactly 32 command clocks and 512 data clocks. All **64 reply bytes matched the pinned working ROM**, with original flash CS# low on every data sampling edge. Mean sampled SPI clock was about **33.34 MHz** (individual sampled periods 29.4–35.3 ns). The command watcher saw 1,836,737 commands with no RX stall, and Fedora returned after the cycle. No BIOS EEPROM or Pico flash write occurred.

The [decoder](../tools/pico2-interposer/analyze_uefi_burst_snapshot.py) and its synthetic 64-byte positive/one-bit-negative check pin the interpretation. The ignored raw snapshot SHA256 is `e0714c82feb8ec26ca2be33aec4a85f6e5bc717b407999eed7a6be4ade218cd9`; analysis JSON SHA256 is `e3dbfb8af2a22e2a377d33421f6eadb5d8fbbc78c6e9e14f8b755057cac0aeeb`; RAM UF2 SHA256 is `e805d29f2dda142b475135e038b7a5614162832c4ec442f854726f23050d191c`. This measurement establishes transaction length and timing, not that a 64-byte active Pico reply would meet timing or that the unflashed UEFI control works.

## Exact-original active 64-byte handoff

An initial [queued-route selector](../tools/pico2-interposer/burst_select_od.pio) failed on the board because its model treated `PULL` with autopull as an unconditional FIFO consumption. The RP2350 datasheet instead specifies that `PULL` is a no-op when autopull has filled the output shift register. The model now reproduces that behavior and the corrected selector passes a three-read digital replay. A passive boot of the corrected selector reached Fedora; one active exact-original trial also reached Fedora, but a repeat did not route the intended first target and failed closed. Its snapshot showed the target still on the original flash with the queued reply full. The PDU/USB recovery restored Fedora without any BIOS EEPROM or Pico flash write.

The failure exposed a variable command sequence. A fresh **lossless**, input-only RLE capture (SHA256 `10092ddb70fc1d2c77e75e3561d116ceec631389ccddd6fbb729a013e2458410`, 1,836,880 commands, zero overflow/stall) shows `0xae0100 → 0xae00c0 → 0xae0140` on the first pass but `0xae0100 → 0xae0140` on the second. The prior complete capture showed the intervening `0xae00c0` on both passes. Therefore a fixed number of PASS tokens between trigger and target is not a reliable selector.

The [late address-matching selector](../tools/pico2-interposer/burst_match_late_od.pio) keeps the original flash selected while it reads the first 31 command bits. It releases flash CS# only when they match `READ03 0xae0140 >> 1`; it checks the aligned final address bit before enabling Pico MISO. The [exact-original control](../tools/pico2-interposer/burst_match_control.c) preloads its 64-byte reply and bounds the DMA to 15 additional words. Its PIO emits a separate completion IRQ after the 512th data bit and permanently disables further matches, so a lost software command notification cannot turn the second firmware pass into a false first-pass verification. Digital tests cover both observed read orders, an odd-address fault, bounded eight-word FIFO service, and the captured physical SPI edges. In the physical-edge replay, flash CS# release precedes Pico MISO enable by seven 340 MHz PIO cycles (~20.6 ns), exceeding the Macronix MX25L12872F's specified 8 ns output-disable time; first data has six cycles (~17.6 ns) before its sampling edge. The replay is a timing model, not an oscilloscope measurement of Pico pad voltage.

The RAM-only UF2 (SHA256 `ad2c0e92d7292b339fa91debac0464c4ea814d874bc1830b58cebb615cf8cd62`) was staged on the Pi. Its passive mode booted Fedora with MISO disabled. Its active mode then substituted **exactly the original** 64 bytes at the first target read: Pico reported `verified=1`, `fault=0`, `dma_remaining=0`, `fifo=0`, and a first-target data snapshot with relay OE=0 and Pico MISO OE=1. Fedora returned, and the later target read remained on the original flash. This establishes a reversible 64-byte handoff. It does **not** test either DF-lock candidate or video decoding. Neither BIOS EEPROM nor Pico flash was written by these trials.

The first unflashed DF-lock candidate differs from the working ROM at 1,378,304 bytes between SPI `0xae0088` and `0xc31f58`. Of the fresh boot's 21,708 unique 64-byte region reads, 21,671 overlap changed bytes; substituting them requires 1,386,944 bytes of response data. This is larger than the Pico 2's 520 KB SRAM. The 4 MB on-board QSPI flash can hold that payload; the single-burst XIP/DMA timing check below now passes. The equal-length offline variant described below removes the first candidate's early short-read and changed-tail requirements. The DF-lock call remains an unproven hypothesis, and neither candidate should be written to the BC250 BIOS EEPROM on this evidence.

## Read-only Pico XIP throughput and inter-burst gap

A RAM-only [on-chip SPI/XIP bench](../tools/pico2-interposer/burst_xip_bench.c) used unwired Pico GP8–GP12 while the BIOS flash CS# relay stayed active. **Correction:** the first reported 34/42.5 MHz passes were false positives. `picotool load -x` did not initialize QMI/XIP for the `no_flash` RAM image, so both the expected and captured data were zeros. The corrected image calls `flash_start_xip()`, selects the Pico ROM 0x0B read mode, and uses an independent nonzero source oracle. It passed 1,000/1,000 single-burst replies at 34 MHz; 42.5 MHz failed on the first word. A separate candidate-first-block oracle also passed 1,000/1,000 at 34 MHz. This establishes local throughput at the measured ~33.3 MHz BC250 rate, not on-board data integrity across a full boot.

A separate RAM-only [input-only gap counter](../tools/pico2-interposer/cs_gap_timing.c) kept the original-flash relay and measured CS# high intervals at 340 MHz PIO clock during a PDU boot. Its first trigger had included an earlier 4-byte scan and filled the bounded DMA window before the final few hundred long reads. The corrected second-occurrence trigger covered the whole first contiguous 64-byte UEFI pass: 21,610 internal gaps, **minimum ~1,071 ns, median ~1,076 ns, maximum ~1,106 ns**, with ~6 ns counter resolution. `end=21689 < 22000` confirms no buffer truncation of this interval; the command sniffer saw 1,836,879 commands with no RX stall, and Fedora returned. The gap counter UF2 SHA256 is `ae188d25cd48d2aae2e8f823c2726753e7a5bbf2a714b17597de291fd5eda1ad`. This establishes about 1 µs of preparation time between adjacent long reads, not yet that software can rearm the selector within it.

## Consecutive original-byte control

The RAM-only [Pico-only repeated-read bench](../tools/pico2-interposer/burst_rearm_bench.c) used a PIO host at 34 MHz, a separate PIO reply, a third PIO capture, and an independent CS# gap counter. **Correction:** its earlier 1,024-read passes were also zero-data false positives before QMI/XIP initialization. The corrected bench initialized fast XIP and SHA256-checked the first 64 KiB of the actual candidate payload against an independently generated digest. It then returned all 16,384 expected words from 1,024 increasing-address 64-byte reads at a ~1,064 ns steady CS# gap, with maximum rearm 52 Pico cycles and no DMA, FIFO, or routing fault. The earlier reported 605 ns pass has not been repeated with real bytes. These are local digital tests, not BC250 on-wire measurements.

The [16-burst board control](../tools/pico2-interposer/burst_sequence_control.c) then used a private, ignored [generator](../tools/pico2-interposer/prepare_original_burst_sequence.py) to extract 16 consecutive **unchanged** 64-byte responses from the pinned working ROM. It used the same board-proven address-match PIO, and core1 only rearmed the next address after the previous reply's completion IRQ. **Two separately armed active PDU boots** each completed all **16/16** replies with `fault=0`, DMA remaining 0 and TX FIFO 0. Longest observed rearm was **133** and **137 Pico cycles** (~391 and 403 ns), inside the measured minimum ~1,071 ns gap. Fedora came back over SSH after both. The board-control UF2 SHA256 is `62e304ffa9c84107cef8c9322930b88838c6013e88ebda3e5f9bc8d7d9d56c26`; the private generated-header SHA256 is `3d392ae405af0dd028bdefc0bb5d5b0cc03e36fefdf2051f56e967b7fd6f2949`. An intervening PDU boot also reached Fedora after the one-shot control stopped substituting, testing its pass-through fallback. Neither flash chip was written.

At this stage, the first, longer DF-lock ROM candidate had not been tested. The lossless command traces showed an earlier four-byte-address scan through `0xae0000..0xae00bc` before the long UEFI burst pass; this included three four-byte words changed by that first candidate at `0xae0088`, `0xae008c` and `0xae0090`. Two captures also differed in whether an early 64-byte `0xae0080` read occurred before the long run. The later equal-length variant removed these early changes and was tested through the full-stream interposer, as reported at the top of this note. Neither variant is justified for a BIOS EEPROM flash.

## Early scan timing and equal-length offline variant

The [two-trace coverage audit](../tools/pico2-interposer/analyze_df_lock_overlay_coverage.py) pins both clean and first-candidate ROM hashes. Each trace contains two 48-command early scans with the three changed four-byte words, followed by two regular 21,612-read 64-byte streams. Those original streams end at SPI `0xc31c40`, **before 788 changed bytes** in the first candidate. A candidate with a larger compressed file may therefore request additional reads that cannot be predicted from the original boot trace. The two ignored reports are `overlay-coverage-20260928.json` and `overlay-coverage-same-length-20260928.json` in this directory.

A RAM-only [passive short-gap probe](../tools/pico2-interposer/cs_gap_timing.c) measured 45 internal gaps in the first four-byte scan: **minimum 176 ns, median 235 ns, maximum 90,176 ns**, at ~6 ns resolution. It saw 1,836,934 commands, no RX stall, and Fedora returned. The previously proven ~391–403 ns software rearm cannot safely serve consecutive changed short words. The [autonomous three-word PIO selector](../tools/pico2-interposer/short_scan_sequence_od.pio) passes a synthetic replay at the measured minimum gap with exact original reply bytes and a pass-through sentinel. Its first RAM-image load did **not** re-enumerate the Pico over USB, so this short-word control was **not** run on the BC250. It is no longer needed for the equal-length variant.

The [equal-length generator](../tools/vcn-psp-diagnostics/prepare_same_length_df_lock_control.py) recompresses the same five-byte DF-lock control with LZMA `nice_len=273`. The stream is **243 bytes shorter** than the original; trailing `0xff` fills the original compressed-file length. The firmware file header, GUID-defined section header, compressed-file length, and every SPI byte before `0xaede82` match the working ROM. The embedded LZMA stream decompresses to exactly the already validated patched inner volume, and the independent `uefi_firmware 1.16` parser finds `AmdPspDxeV2` with no decompression error. The unflashed same-length ROM SHA256 is `ae9145cfa521107ebb7e553c39877a89f822ea1960e16f83a38485b9b5fe2331`. Parser acceptance alone did not establish BC250 boot behavior; the later interposer candidate boot reached Fedora but left VCN unavailable.

The outer FFS header has attributes `0x00` and fixed file-checksum byte `0xaa`; its header checksum is valid. The GUID-defined LZMA section requests processing and carries no authenticated-status attribute. The generator now rejects other header forms and verifies that decoding reaches the LZMA end marker with exactly 243 unused `0xff` bytes. EDK II's [FFS definition](https://github.com/tianocore/edk2/blob/master/MdePkg/Include/Pi/PiFirmwareFile.h) defines the fixed checksum when the file-checksum attribute is clear; its [LZMA guided-section decoder](https://github.com/tianocore/edk2/blob/master/MdeModulePkg/Library/LzmaCustomDecompressLib/LzmaDecompress.c) passes the supplied length to `LzmaDecode` and checks its status, not that it consumed every input byte. That supports the padding format, and the subsequent candidate interposer boot reached Fedora. It did not enable VCN.

Both complete command traces show **zero** changed four-byte scan words and **zero** changed bytes beyond the original long stream for the equal-length variant. The [schedule replay](../tools/pico2-interposer/test_df_lock_stream_schedule.py) covers the two observed 20,727-read passes. The [private payload generator](../tools/pico2-interposer/prepare_same_length_payload.py) made the 1,327,104-byte candidate payload at Pico QSPI offset `0x200000`; the [selector](../tools/pico2-interposer/df_lock_stream_control.c) SHA256-checks that complete payload before arming. The first candidate trial and a subsequent [exact-original control payload](../tools/pico2-interposer/prepare_original_stream_control.py) both stopped after one pass with the older, late-release selector; this was an interposer timing problem. The original-control RAM UF2 SHA256 was `f95241499089bc8cc2356ae33bff804932fdf7accefdf6fd4db9c6b6d75f5bac` and QSPI payload SHA256 was `a920ee83a043ae2f916846b32fd680d90612ac8e9060afe5fe5fd411046cc092`.

The Pi 5 restart recovered the Pico USB device without physical BOOTSEL intervention. The [early-release selector](../tools/pico2-interposer/burst_match_early_od.pio) fixed the full-stream control: exact-original responses completed both passes and booted Fedora. A candidate boot then completed both passes; the final revision's input-only sampler measured a byte-exact 64-byte second-pass response. Nevertheless, the kernel listed no VCN IP block and VA-API could not initialize. Directly mapping the GPU BAR5 MMIO for a read caused the BC250 to stop responding on an earlier candidate boot; that procedure must not be repeated. A later PCI-config SMN-only read showed `0x50d6c=0xf0`, and the board was recovered through passive Pico CS# relay plus a PDU cold cycle. A decoded hardware video frame is still outstanding.
